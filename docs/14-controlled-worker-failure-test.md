## Controlled Worker Failure Test

### Objective

Validate the complete observability and recovery chain when a Kubernetes worker node becomes unavailable.

The test validates:

* Kubernetes node failure detection
* Prometheus target monitoring
* Prometheus alert evaluation
* Alert transition from `pending` to `firing`
* Workload continuity on the remaining nodes
* Worker node recovery
* Automatic alert resolution
* Final platform health

This is a **controlled failure test** performed on `k8s-worker-2`.

---

### Initial state

Before the failure, the platform was healthy:

```text
k8s-cp         Ready
k8s-worker-1   Ready
k8s-worker-2   Ready
k8s-worker-3   Ready
```

The platform health check returned:

```text
OK   : 27
WARN : 0
FAIL : 0

Platform Lab: HEALTHY
```

Prometheus initially reported only the expected `Watchdog` alert:

```text
ALERT : Watchdog
STATE : firing
```

`Watchdog` being permanently `firing` is expected. It acts as a heartbeat indicating that the Prometheus/Alertmanager alerting chain is operational.

---

### Failure injection

`k8s-worker-2` was deliberately powered off from the Proxmox host.

The Kubernetes cluster subsequently reported:

```text
k8s-cp         Ready
k8s-worker-1   Ready
k8s-worker-2   NotReady
k8s-worker-3   Ready
```

The node description showed:

```text
node.kubernetes.io/unreachable:NoExecute
node.kubernetes.io/unreachable:NoSchedule
```

and:

```text
Ready          Unknown
MemoryPressure Unknown
DiskPressure   Unknown
PIDPressure    Unknown
```

with:

```text
Reason: NodeStatusUnknown
Message: Kubelet stopped posting node status.
```

This confirms that Kubernetes detected the worker as unreachable rather than merely reporting a transient application failure.

---

### Prometheus detection

Prometheus initially reported several alerts as `pending`.

Relevant alerts included:

```text
TargetDown
KubePodNotReady
KubeNodeNotReady
KubeNodeUnreachable
KubeletInstanceUnreachable
KubeDaemonSetRolloutStuck
KubeDaemonSetMisScheduled
KubeDeploymentReplicasMismatch
```

The important node-related alerts were:

```text
KubeNodeNotReady
KubeNodeUnreachable
KubeletInstanceUnreachable
```

Their configured evaluation delays were verified through the Prometheus rules API:

```text
TargetDown                  FOR: 600s
KubeNodeNotReady            FOR: 900s
KubeNodeUnreachable         FOR: 900s
KubeletInstanceUnreachable  FOR: 900s
```

Therefore:

* `TargetDown` becomes `firing` after approximately 10 minutes.
* The node/kubelet alerts become `firing` after approximately 15 minutes.

This demonstrates that the alerting rules deliberately tolerate short-lived interruptions before declaring a persistent incident.

---

### Alert firing

After the configured delays, Prometheus reported the worker failure as active:

```text
ALERT : KubePodNotReady
ALERT : KubeDaemonSetRolloutStuck
ALERT : KubeDaemonSetMisScheduled
ALERT : TargetDown
ALERT : KubeNodeNotReady
ALERT : KubeNodeUnreachable
ALERT : KubeletInstanceUnreachable
ALERT : Watchdog
```

`Watchdog` remained `firing` throughout the incident and was not related to the worker failure.

The other alerts were generated as a direct consequence of `k8s-worker-2` being unavailable.

This validates that Prometheus can detect the failure through several independent signals.

---

### Workload behaviour during the failure

While `k8s-worker-2` was unavailable, Kubernetes continued operating the cluster using the remaining nodes.

Workloads originally scheduled on the failed node were progressively rescheduled where their deployment configuration allowed it.

DaemonSets such as:

* MetalLB FRR
* MetalLB speaker
* Prometheus node-exporter

were recreated automatically when the node returned.

This confirms that the cluster maintains workload continuity despite the loss of one worker.

---

### Worker recovery

`k8s-worker-2` was powered on again from Proxmox.

The node automatically returned to:

```text
k8s-worker-2   Ready
```

The complete cluster subsequently reported:

```text
k8s-cp         Ready
k8s-worker-1   Ready
k8s-worker-2   Ready
k8s-worker-3   Ready
```

The worker's infrastructure DaemonSets also returned:

```text
metallb-frr-k8s-*       Running
metallb-speaker-*       Running
prometheus-node-exporter-* Running
```

---

### Alert resolution

After recovery, the Prometheus alerts generated by the failure disappeared.

The only remaining active alert was:

```text
ALERT : Watchdog
STATE : firing
```

This is the expected steady-state condition.

Therefore, the failure alerts were automatically resolved without manual intervention.

---

### Final platform health

The final health check returned:

```text
========================================
 Summary
========================================
OK   : 27
WARN : 0
FAIL : 0

Platform Lab: HEALTHY
```

All of the following were confirmed:

* Terraform state accessible
* Git repositories clean
* SSH connectivity to all nodes
* K3s services running
* Kubernetes API reachable
* all Kubernetes nodes `Ready`
* Flux healthy
* Flux Kustomizations ready
* Flux HelmReleases ready

---

### Test result

**PASS**

The Platform Lab successfully detected, reported, tolerated, and recovered from the controlled loss of a Kubernetes worker.

The validated operational chain is:

```text
Worker failure
      │
      ▼
Kubernetes NodeNotReady
      │
      ▼
Prometheus detection
      │
      ├── TargetDown
      ├── KubeNodeNotReady
      ├── KubeNodeUnreachable
      ├── KubeletInstanceUnreachable
      └── workload-related alerts
      │
      ▼
Alerts become firing
      │
      ▼
Worker recovery
      │
      ▼
Kubernetes NodeReady
      │
      ▼
Workloads recover
      │
      ▼
Prometheus alerts resolve
      │
      ▼
platform-health.sh
      │
      ▼
Platform Lab: HEALTHY
```
